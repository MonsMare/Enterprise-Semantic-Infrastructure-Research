# Knowledge Runtime 混合检索迭代结果

本轮按“段落级证据索引 + 词项与本地相似度混合排序”完成一轮离线迭代。目标是让检索结果直接定位可读取、可引用的证据段，而不是只返回文档窗口；评测同时检查真实公开精算文档、弱查询和 5,000 份合成语料下的行为。

## 本轮实现

- SQLite 为每份当前 revision 建立标题、段落、页标记和原文行范围对应的 chunk，并通过 revision 绑定 Locator。
- 搜索把 FTS5 的名称/标题/正文排序与本地确定性字符 n-gram 稀疏向量的精确余弦排序用 RRF 合并。稀疏向量压缩为 SQLite BLOB；该 encoder 是词形相似度代理，不是训练过的 dense embedding，也不调用云端模型。
- 修正评测器：分别记录来源排名和证据 chunk 排名，按实际全局 chunk rank 读取目标来源，并在 gold evidence 已齐时停止。没有 gold evidence 标注的 case 不混入证据排名指标。
- 修正 FTS5 BM25 列权重、避免每次启动都重建有效的 chunk FTS 投影，并补足自定义向量维度、语义-only 召回、大小写敏感查询和弱查询碰撞的回归测试。
- v6 数据迁移移除旧的逐坐标关系型 posting 表。此前 1,412 个 chunk 的 posting 表和索引合计约 162 MB，主要由重复存储长 chunk ID 和多棵 B-tree 引起。新方案保留压缩向量，在 POC 规模上做精确扫描。

## 公开精算文档结果

本机 benchmark 库有 10 份公开来源文档、1,412 个当前 chunk。新报告由 retrieval-only 命令生成，没有模型调用。

报告中的 Evidence rank 是 oracle-style 的检索诊断：评测器按全局搜索排名读取预期来源的 chunk，跳过非预期来源来测 gold evidence 需要到达的位置。它不模拟 Agent 实际逐项选择候选、读取预算和调用轮数。

| 集合 | 结果 | 解释 |
|---|---:|---|
| 精确问题，4 个 | 来源 Hit@1 4/4；MRR 1.000 | 四个问题的预期来源均排首位 |
| gold evidence 定位，4 个 | Evidence 找全 4/4；Evidence Hit@1 2/4、Hit@3 3/4、MRR 0.656 | ASOP 23 的完整支持证据需要读到第 8 个目标来源 chunk；ASOP 43、ASOP 56 分别在第 1 位，EIOPA 在第 2 位 |
| 模糊/简短 gold 检索，4 个可回答问题 | 来源 Hit@1 4/4；Evidence 找全 4/4 | 这是人工写好的 `retrieval_query` 直接测 KR，不代表 Qwen 已成功把中文用户问法改写成这些查询 |
| 无上下文问题，2 个 | 两题均返回空结果 | “那四种？”和“这个怎么弄？”不会只凭当前知识库内容生成证据支持的回答 |
| 单词级弱查询，4 个 | 来源 Hit@1 3/4、Hit@3 4/4、MRR 0.875 | 来源找到不等于证据片段足够靠前：证据首次完整出现排名为 29、5、36、10；四题均未达到 Evidence Hit@3 |

上一版 source-level 报告也是 4/4 来源 Hit@1。它没有证据 chunk 排名指标，只读取较短文档窗口；因此新旧 Evidence 字节数不能直接比较。新报告的端到端 p50 为 176.6 ms，p95 为 381.0 ms；旧报告 p50 为 288.2 ms，p95 为 302.5 ms。每组只有 4 个不同问题，p95 对单次慢查询很敏感，不能据此断言延迟稳定下降。

## 语料规模和资源成本

同一套确定性合成数据在 20、100、1,000、5,000 份文档上运行；每个规模有 20 个目标文档、40 个独立查询，执行两轮并预热一轮。报告中的数据库大小是新建临时库的文件大小。

| 文档数 | 新库大小 | 建库时间 | Search p50 / p95 |
|---:|---:|---:|---:|
| 20 | 0.35 MB | 0.06 s | 3.9 / 4.4 ms |
| 100 | 1.36 MB | 0.32 s | 17.2 / 19.4 ms |
| 1,000 | 12.41 MB | 3.83 s | 142.9 / 155.4 ms |
| 5,000 | 61.42 MB | 45.37 s | 732.5 / 767.6 ms |

在 5,000 份语料下，文档特征足够明确的精确查询在 top-3 的目标来源命中率为 100%，Evidence 原文定位率为 95%。与旧 FTS-only scale 报告相比，新方案的精确查询 Hit@1 从 100% 降至 60%，Hit@3 保持 100%，MRR 从 1.000 降至 0.758；新方案增加了段落粒度和相似度排序，但首位排序还不够稳定。旧版按整份文档排名，新版按 chunk 排名并用来源首个命中 chunk 计算来源排名，所以 Hit@k/MRR 只能作为方向性对照，不能视为完全等价的受控消融实验。

资源代价也明确：相同规模下，新方案文件约 61.42 MB，旧 FTS-only 文件约 8.05 MB（约 7.6 倍）；建库从 8.65 秒增至 45.37 秒（约 5.2 倍）；Search p50 从 435 ms 增至 732 ms（约 1.7 倍），p95 从 679 ms 增至 768 ms（约 1.1 倍）。当前语义阶段是遍历当前 chunk 的精确余弦扫描，时间和临时工作集随 chunk 数增长；它适合 POC 基线，不是 5,000+ 文档的最终索引结构。

宽泛控制问题故意只包含所有文档共享的“actuarial / capital / claim / reserve”等词，指定的 gold 文档无法从查询中辨认。此类目标命中率不是正确率；它只说明查询缺少区分信息，不应拿它评价解析器或 Agent。

## 迁移后的数据库空间回收

v6 的 `DROP TABLE` 能删除旧 posting 逻辑数据，但 SQLite 不会因此自动缩短文件。当前公开精算库升级后仍有 39,814 个空闲页，数据库物理大小 175.47 MB；在离线维护窗口执行 `VACUUM` 后，文件缩至 11.51 MB，10 份来源和 1,412 个当前 chunk 均保留。对其他已升级库，需要在确认没有并发写入后自行安排 `VACUUM`；不要把启动时自动全库重写作为普通迁移步骤。

## 结论和下一步

这轮证明 KR 可以把来源排名与可引用证据位置分开评测，并能在真实精算文档的精确查询中稳定找对来源。现阶段“找到了相关文档”仍不能代表弱查询下高效取得答案所需的证据：单词查询的 Evidence rank 仍为 5–36。资源结果也显示，当前完整稀疏扫描相比 FTS-only 增加了建库时间、文件体积和中位检索时延。

真实 Qwen Agent 迭代报告本轮没有生成：运行进程中没有配置 `LLM_API_KEY`，而仓库约定只从环境读取密钥。模糊数据集的离线结果只覆盖人工 gold query 到 KR 的检索，不覆盖 Agent 查询改写、答案质量或回答中的 Evidence 引用。后续应先在本机配置密钥并单独跑 Qwen 3.8 Agent benchmark，再依据真实 Agent 查询日志优化弱查询改写；检索侧则需要以可控的稀疏特征候选索引加精确余弦重排替代全量扫描，并保持当前 Evidence rank 指标作为质量门槛。
